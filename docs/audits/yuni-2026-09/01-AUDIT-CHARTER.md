# Yuni — Audit Charter

Дата: 2026-09-06. Протокол для основной модели, sub-agent’ов и финального reviewer-а.

## 1. Purpose

Провести технический аудит Yuni с проверяемыми выводами и сформировать применимый remediation backlog. Превратить результаты сильной модели в долговременную инженерную память: принятые решения, invariants, правила проверки и reference implementations для дальнейшей работы менее мощных моделей.

[Pre-Audit Plan](00-PRE-AUDIT-PLAN.md) хранит план и журнал подготовки; этот документ определяет порядок получения и принятия результатов, но не подтверждает реализацию функций.

Scope-check создания charter: только этот Markdown-файл, без запуска аудита, findings о проекте, изменений кода или коммита. `AGENTS.md` не изменяется по прямому ограничению владельца: charter конкретизирует данный аудит, не заменяя общие Git, security и quality-gate правила.

## 2. Audit baseline

- Ветка подготовки: `chore/pre-audit-setup`.
- Audit commit: **Pending**. До фиксации полного commit SHA выводы не считаются результатами аудита baseline.
- Основная модель фиксирует SHA, состояние рабочего дерева, версии инструментов, команды, окружение без секретов и результаты применимых checks. Все агенты получают один SHA; runtime и CI evidence должны быть привязаны к нему.
- Изменять код, тесты и конфигурацию во время read-only проходов запрещено. Отчёты сохраняются только в согласованных audit-артефактах. Исправления выполняются отдельными задачами после аудита.
- Проверки с записью данных, migrations и сборки выполняются только в заранее согласованном изолированном окружении с synthetic fixtures; рабочие данные и baseline checkout не изменяются. Mutation testing требует отдельного scope и отдельной копии.
- Для каждого check записывать команду, дату, exit code, итог `passed / failed / blocked / not-run` и безопасное evidence. `blocked` и `not-run` не означают успех. При смене SHA повторно определить затронутые проверки, не смешивать результаты разных baseline.

## 3. Scope

| Domain | Что оценивается |
| --- | --- |
| Architecture and spaghetti code | Границы модулей, зависимости, циклы, связанность, дублирование, смешение ответственности и стоимость изменений. |
| Frontend | React/Next.js boundaries, состояние, UI-сценарии, accessibility, loading/error states и visual QA по `CLAUDE.md`. |
| Backend and API | NestJS, DTO, контракты, сериализация, ошибки и бизнес-правила. |
| Database | Prisma schema, migrations, constraints, индексы, транзакции и согласованность данных. |
| Testing reliability | Сила assertions, границы mock-ов, negative/boundary/race cases, flaky tests и реальные интеграции. |
| Security and data integrity | Authentication, authorization, owner checks, privacy, block/report, rate limits, media safety и защита PII. |
| Performance | Измеряемые задержки, N+1, pagination, ресурсы, объём запросов и frontend rendering; одинаковые условия замеров. |
| DevOps and CI/CD | Воспроизводимость сборки, Docker, конфигурация окружения, pipeline и production readiness. |
| Documentation and AI context | Соответствие утверждений evidence, ADR, навигация, устаревание и пригодность инструкций для AI. |

## 4. Out of scope

- Массовый рефакторинг и автоматические исправления во время аудита.
- Изменение продукта без отдельного решения владельцев.
- Переписывание работающих частей только ради другого стиля.
- Автоматическое принятие общих best practices без проверки применимости к Yuni.

## 5. Evidence hierarchy

Порядок доверия к evidence в рамках этого аудита, при сопоставимых SHA, окружении и сценарии:

1. Воспроизводимое runtime-поведение.
2. Production code и доступная конфигурация без секретов.
3. Database schema и migrations.
4. Tests: assertions, фактическое исполнение и границы подмен.
5. CI/CD: конфигурация и результаты конкретного запуска.
6. Documentation и исторические отчёты.

Документация — источник заявлений и намерений, а не доказательство реализации. Успешный mock-тест не доказывает поведение PostgreSQL; зелёный CI не доказывает сценарий, который не исполнялся. Runtime-наблюдение без установленного SHA/окружения не вытесняет проверенное evidence.

Этот порядок оценки доказательств задан владельцем для аудита; общие источники истины и правила работы остаются в [AGENTS.md](../../../AGENTS.md). Противоречие требует дополнительной проверки по разделу 9, а не автоматического выбора удобного источника.

### Positive Assurance

Отсутствие finding и зелёные тесты сами по себе не доказывают корректность. Assurance относится только к ограниченному invariant/scope и связывается с полным commit SHA, окружением, датой, воспроизводимым evidence, негативными проверками и границами покрытия; результаты оформляются по [Assurance Register](06-ASSURANCE-REGISTER.md) после независимого review.
Изменение связанного кода, schema, configuration, dependency или policy запускает перепроверку и может инвалидировать assurance; до проверки её нельзя переносить на новую версию автоматически. Assurance candidates возвращаются в отчёте; запись в реестр требует явного разрешения.
Условный отсутствующий компонент можно закрыть как `N/A — absence verified` только с evidence отсутствия/неприменимости на указанном SHA, обычно в checklist mapping. Отсутствие условной технологии не является finding; N/A не является positive assurance.

## 6. Rules for findings

Один finding описывает одну первопричину и её последствия. Основные поля таблицы ниже обязательны; неприменимое поле содержит `N/A` с причиной. Дополнительные условные поля detailed template в `03-FINDINGS.md` включаются только по применимости. Наблюдение, гипотеза и рекомендация явно разделяются.

| Поле | Требование |
| --- | --- |
| ID | Стабильный `YUNI-202609-<DOMAIN>-NNN`; основная модель назначает domain-коды до делегирования, ID не переиспользуется. |
| Domain | Одна основная область из Scope; смежные области указываются дополнительно. |
| Title | Конкретный дефект или проверяемое утверждение. |
| Severity | `P0–P3`, с обоснованием последствий и условий возникновения. |
| Confidence | `High`: воспроизводимое либо однозначное прямое evidence; `Medium`: цепочка evidence с непроверенным условием; `Low`: гипотеза. |
| Affected files and symbols | Пути относительно репозитория, символы и строки на audit SHA. Для инфраструктуры — конкретный job/service/config key. |
| Current behavior | Наблюдаемое поведение и ожидаемый invariant/контракт с источником ожидания. |
| Evidence | Audit SHA, точные ссылки, минимальный безопасный фрагмент или результат команды; ограничения наблюдения. |
| Risk | Кто/что затронуто, масштаб, вероятность и последствия; условия эксплуатации, если применимо. |
| Reproduction or verification method | Предусловия, synthetic inputs, шаги/команды, ожидаемый и фактический результат. Невыполненную проверку явно пометить. |
| Recommended solution for Yuni | Минимальное исправление причины с учётом существующей архитектуры и ограничений. |
| Alternatives considered | Реальные альтернативы, включая отсутствие изменения, и причины выбора. |
| Tests required | Проверяемые invariants, тип теста, negative/boundary cases и применимые checks; без автоматического добавления тестов. |
| Documentation impact | Какие ADR, инструкции, task docs или references потребуют обновления и почему. |
| Status | Стадия рассмотрения и, после подтверждения, lifecycle-статус по правилам ниже. |

Стадии рассмотрения: `Proposed` → `Confirmed` или `Rejected`. Только reviewer переводит в `Confirmed` после проверки evidence. Confidence не заменяет severity или подтверждение.

Для подтверждённых findings применять lifecycle из [Audit Index Process](../README.md): `verified`, `needs-recheck`, `deferred`, `resolved`, `false-positive`. Формат поля: `Confirmed / verified`. `resolved` требует отдельного fix commit и успешной повторной проверки; аудит сам ничего не исправляет.

`Proposed` не публикуется как подтверждённый finding. `Rejected` хранит основание; в audit index он попадает как `false-positive` только при доказанном опровержении. Недостаток evidence оставляет `Proposed`, а не означает отсутствие дефекта. Для index обязательны related task либо явно обоснованный `deferred`/`false-positive`, дата и условия recheck.

Запрещено включать `.env`, secrets, tokens, cookies, PII, реальные фотографии, сообщения и dumps. Использовать synthetic placeholders и безопасные выдержки. CodeGraph помогает навигации; результат графа проверяется по исходнику на audit SHA.

## 7. Severity definitions

| Severity | Критерий |
| --- | --- |
| P0 | Критическая безопасность, потеря/утечка данных, обход авторизации или неработоспособность ключевого сценария. |
| P1 | Серьёзная ошибка бизнес-логики или высокая вероятность production-инцидента. |
| P2 | Значимый технический долг, слабая тестируемость, высокая связанность либо существенная проблема производительности. |
| P3 | Cleanup, локальная читаемость и небольшие улучшения. |

Приоритет определяется доказанным риском, охватом и условиями возникновения. Размер файла или субъективно некрасивый код сами по себе не определяют высокий приоритет; performance finding требует замера или обоснованной модели роста.

Для совместимости с [AI Review Protocol](../../AI_REVIEW_PROTOCOL.md): `P0 → critical`, `P1 → high`, `P2 → medium`, `P3 → low`; `info` — контекст без дефекта, а не отдельный приоритет. Исторические записи автоматически не переклассифицируются.

## 8. Sub-agent protocol

Основная модель до запуска назначает владельца области, audit SHA, точные пути, вопросы, разрешённые проверки, ID-префикс и выходной артефакт. Агенты не расширяют scope и не исправляют находки автоматически. Общие файлы/окружения не изменяются параллельно.

| Role | Границы ответственности |
| --- | --- |
| Baseline | SHA, среда, реальные scripts/checks, результаты и блокеры воспроизведения; без исправления проваленных checks. |
| Architecture and Spaghetti Code | Граф зависимостей, границы ответственности и причины сложности; без рефакторинга. |
| Test Reliability | Assertions, моки, пропуски и flaky cases; отделить наличие теста от силы доказательства. |
| Security and Data Integrity | Доступ, privacy, PII, abuse, media и race/rollback invariants; только synthetic data. |
| Backend/API/Database | Контракты, сервисы, queries, schema/migrations, constraints и производительность БД; без запуска несогласованных migrations. |
| Frontend | UI-сценарии, состояние, server/client boundaries, accessibility, rendering performance и visual evidence. |
| DevOps/Production Readiness | Docker, CI/CD, environment loading, наблюдаемость и восстановление; оценка готовности без deployment. |
| Documentation/AI Context | Проверить утверждения и ссылки, ADR и инструкции; исторический отчёт не подтверждает текущее покрытие. |
| Synthesis and Red-Team Reviewer | Независимо проверить evidence и контрпримеры, объединить дубли, разрешить triage и собрать synthesis/backlog. |

Каждый агент возвращает coverage своей области, выполненные и невыполненные checks, Proposed findings и открытые вопросы. Performance распределяется между соответствующими ролями; основная модель проверяет отсутствие пробелов Scope.

Первый независимый review — blind по `AI_REVIEW_PROTOCOL.md`: reviewer получает charter, SHA/diff, файлы, документы и checks, без executor chat и скрытых рассуждений. Затем допускается cross-review отчётов и кратких обоснований. Подтверждение автора не заменяет независимый review.

## 9. Duplicate and contradiction handling

- Пересечения допустимы. Финальный reviewer объединяет findings с общей причиной, сохраняет исходные ID как aliases, ссылки на evidence и отдельные последствия; похожие симптомы разных причин не сливаются.
- Конфликтующие выводы не разрешаются голосованием или авторитетом модели. Сначала сверить SHA, среду, предусловия и определения, затем повторить минимальную проверку.
- До решения не выполнять зависящие от спорного вывода действия. Неразрешённое противоречие фиксируется с evidence и передаётся владельцам по `AGENTS.md`.
- Неподтверждённое остаётся `Proposed`; опровергнутое или отклонённое с явным основанием — `Rejected`. В synthesis сохраняются ограничения и открытые вопросы, а не выдуманный консенсус.

## 10. Best-practice acceptance process

Finding → Candidate → Проверка применимости к Yuni → Проверка официальных источников и альтернатив → Cross-review → Accepted или Rejected → ADR / engineering guideline / AGENTS.md / skill / reference implementation.

Для Candidate записать исходные finding IDs, проблему Yuni, пользу, стоимость внедрения, альтернативы, официальные источники с версией/датой и условия пересмотра. Официальная рекомендация сама по себе не доказывает применимость.

Владельцы принимают решение после cross-review. `Accepted` означает принятое решение, а не выполненную реализацию. Best practice не становится обязательным правилом автоматически: обязательность, область применения и источник правила фиксируются отдельно. Изменения ADR, guidelines, `AGENTS.md`, skills и reference implementations выполняются отдельными согласованными задачами; `Rejected` сохраняет причину.

Архитектурные решения оформляются по [ADR Process](../../decisions/README.md), с последствиями, альтернативами и полем «Пересмотреть если». Долговременная память должна ссылаться на evidence и проверенную реализацию, а не копировать рассуждения модели.

## 11. Rules for future AI models

- Безопасность, авторизация, валидация и целостность данных — обязательные invariants; не ослаблять их для прохождения теста или упрощения кода.
- Сначала использовать существующие решения, принятые ADR и reference implementations; проверять их соответствие текущей задаче и SHA.
- Не создавать новую абстракцию без конкретной причины, рассмотрения существующего решения и оценки стоимости сопровождения.
- Отклонение от принятого ADR явно указать и согласовать до реализации; не подменять решение молча.
- Запускать checks затронутой области по [Quality Gates](../../QUALITY_GATES.md) и task scope, используя реальные scripts. Для тестового плана [Critical Test Scenarios](../../testing/critical-scenarios.md) — перечень заявлений для перепроверки.
- Не скрывать неуверенность, отсутствие evidence, недоступные инструменты и пропущенные проверки; отделять факт, гипотезу, решение и future work.

## 12. Definition of audit completion

- [ ] Baseline зафиксирован: точный audit commit SHA, окружение, команды и результаты; `Pending` заменён в метаданных результатов аудита.
- [ ] Все запланированные проходы завершены с явным coverage; блокеры и непроверенные области разобраны, изменение scope согласовано владельцами. `not-run` не выдан за проверку.
- [ ] Все подтверждённые findings имеют evidence на audit SHA и независимый review; Proposed/Rejected отделены от них.
- [ ] Дубли и противоречия рассмотрены, основания решений и оставшиеся ограничения записаны.
- [ ] Сформирован remediation backlog: finding ID, priority, task или обоснованный defer, зависимости, критерии приёмки и recheck.
- [ ] Best-practice candidates рассмотрены: Accepted/Rejected с основаниями и назначенным местом инженерной памяти.
- [ ] Подготовлен итоговый synthesis: SHA, scope/method, coverage, результаты checks, риски, решения, backlog и ограничения выводов.

Завершение аудита не означает исправление всех дефектов, production readiness или завершение remediation. Подтверждённые records оформляются по Audit Index Process; raw drafts не становятся подтверждёнными findings автоматически.
