### Второе срабатывание — не второй баг, а артефакт SPA-навигации

Проверка перехода `/signin` → (клик «Создать профиль», клиентский роутинг
Next.js, без полной перезагрузки) → `/join` → (клик «Войти», снова
клиентский переход) → `/signin`: issue **появляется** на `/signin`.

Но его данные:

```
data={"violatingNodeAttribute":"autocomplete","uid":"16_22"}
```

`uid=16_22` — это узел «ДАТА РОЖДЕНИЯ» со **страницы `/join`**, снятый в
предыдущем `take_snapshot`, не элемент `/signin`. После обычного
`reload()` issue немедленно пропадает.

**Вывод**: панель DevTools Issues не сбрасывается при клиентской
(pushState) навигации Next.js — только при полной перезагрузке страницы.
Инвентаризация 2026-08-20, судя по всему, переходила между `/join` и
`/signin` по ссылкам внутри приложения, и одна и та же находка (birthdate
на `/join`) задвоилась в отчёте под видом второго независимого случая.
**Реальный дефект один.** `auth-shell.tsx` и `auth-field.tsx` (общие
компоненты, вторая проверенная гипотеза) в этом не участвуют — оба чистые,
проверены все 7 полей на обеих формах по отдельности.

## Проверка гипотезы «сочетание с `type`/`inputMode`»

Отдельно проверено и отвергнуто:

| Конфигурация `#birthdate` | Issue |
| --- | --- |
| `type="text"`, `inputMode="numeric"`, `autoComplete="bday"` (исходное) | есть |
| `type="text"`, без `inputMode`, `autoComplete="bday"` | есть |
| `type="date"`, без `inputMode`, `autoComplete="bday"` | **есть** |

Issue не зависит ни от `inputMode`, ни от типа поля — Chrome не признаёт
значение `"bday"` валидным для этого элемента ни в одной из проверенных
конфигураций, хотя по спецификации WHATWG `bday` — легитимный токен.
Список валидных значений в Chrome расходится со спекой (тот же класс
расхождения, что у документированного отдельно случая с `nickname`,
который Chrome тоже не признаёт).

## Правка

`autoComplete="off"` вместо `"bday"` на `#birthdate`
(`birthdate-field.tsx:94`), с комментарием на месте: почему `off`, а не
`bday`, и что настоящее решение (нативный `type="date"` либо три поля
`bday-day`/`bday-month`/`bday-year`) — отдельная задача, не эта.

**Почему `off` не теряет функциональность.** Помимо самого issue,
`handleChange` в том же файле безусловно прогоняет значение через
`digitsOnly(e.target.value)` — берёт все цифры из строки, не разбирая их
исходный порядок. Если бы Chrome всё же попытался подставить дату (в
формате `YYYY-MM-DD`, как это делает автозаполнение для `type="date"`),
маска перемешала бы цифры года/месяца/дня в неверном порядке и записала
бы не ту дату. То есть даже без issue поле в текущем виде не могло бы
корректно принять автоподстановку.

**Что не удалось проверить напрямую.** Живое сохранённое значение `bday` в
автозаполнении Chrome живёт в разделе «Автозаполнение и пароли → Удостоверения
личности», который в этом окружении неактивен без входа в Google-аккаунт
(`chrome://settings/identityDocs` — переключатель и кнопка «Добавить»
задизейблены). Подставить тестовые данные и увидеть подсказку браузера
вручную не получилось — вывод об отсутствии потери функциональности
основан на (1) самом issue (Chrome не считает элемент валидной целью для
автозаполнения) и (2) разборе `handleChange` выше, а не на прямом
наблюдении подсказки автозаполнения.

Автозаполнение остальных полей (email, current-password, given-name,
username, new-password) не тронуто и не пострадало — они не менялись.
