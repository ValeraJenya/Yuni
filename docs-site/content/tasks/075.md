## Почему нельзя чинить механически

Предупреждение стоит на `setVisible(true)` внутри ветки фолбэка:

```ts
// Older engines without IntersectionObserver get the content immediately
// rather than a block that never reveals.
if (typeof IntersectionObserver === "undefined") {
  setVisible(true)
  return
}
```

Эта ветка существует ровно затем, чтобы на движках без
`IntersectionObserver` контент показался сразу, а не остался навсегда
невидимым блоком. Убрать `setState` отсюда «чтобы линтер молчал» — значит
сломать путь деградации и получить пустой лендинг на старых браузерах вместо
предупреждения в консоли сборки.

Два допустимых способа:

1. **Ленивое начальное состояние** — вычислить доступность
   `IntersectionObserver` при инициализации `useState`, чтобы фолбэк не
   требовал `setState` в эффекте вообще.
2. **Точечный `eslint-disable`** на одной строке — с комментарием, объясняющим,
   зачем ветка нужна.

Это записано отдельной задачей и явным текстом именно потому, что следующий,
кто увидит 18 вместо 17, с высокой вероятностью «почистит» предупреждение
самым коротким способом и уберёт фолбэк вместе с ним.

## Scope

Вернуть baseline к 17 одним из двух способов выше, сохранив поведение на
движках без `IntersectionObserver`.

## Проверка гипотезы о гидратации (на реальной сборке)

Перед выбором способа починки была проверена гипотеза из ROADMAP: ленивый
инициализатор `useState(() => typeof IntersectionObserver === "undefined")`
даст расхождение SSR/клиент, потому что `apps/frontend/app/page.tsx` —
`"use client"`, но Next всё равно рендерит его на сервере для начального
HTML, а `IntersectionObserver` на сервере (Node) не существует.

Проверено не рассуждением, а прогоном:

1. `node -e "console.log(typeof IntersectionObserver)"` → `undefined` —
   подтверждает, что на сервере ветки фолбэка нет.
2. Ленивый инициализатор был временно применён, `.next` пересобран, dev-сервер
   перезапущен.
3. `curl http://localhost:<port>/` показал `data-visible="true"` на всех 18
   `[data-reveal]`-элементах в SSR-HTML (сервер видит "нет
   `IntersectionObserver`" и сразу помечает всё видимым).
4. В консоли браузера после гидратации — реальная ошибка React:

   > A tree hydrated but some attributes of the server rendered HTML didn't
   > match the client properties. This won't be patched up.
   > ...
   > `data-visible="false"` (client) / `data-visible="true"` (server) — на
   > каждом `InView`-инстансе (`Manifesto`, `Safety`, `CtaSection`, `Support`,
   > `PinkRabbit`).

Гипотеза подтвердилась прогоном, а не рассуждением. Ленивый инициализатор
отпадает: он не убирает предупреждение линтера ценой скрытой поломки
гидратации на каждой странице лендинга — это хуже, чем текущее
предупреждение. Изменение отменено, `in-view.tsx` возвращён к исходному
`useState(false)`.

## Применённое исправление

Точечный `eslint-disable-next-line react-hooks/set-state-in-effect` на
`setVisible(true)` внутри ветки фолбэка, с комментарием, объясняющим ветку
и почему ленивая инициализация не подходит (см.
`apps/frontend/components/landing/motion/in-view.tsx:40-51`) — комментарий
адресован тому, кто через полгода снова попробует «почистить»
предупреждение самым коротким способом.

Фолбэк-путь после правки проверен вживую: `IntersectionObserver` удалён из
`window` через `initScript` при навигации, страница перезагружена — все 18
`[data-reveal]`-элементов получили `data-visible="true"` сразу, новых ошибок
и предупреждений в консоли не появилось.
