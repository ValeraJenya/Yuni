## Finding

`ChatMessageView` на бэкенде (`chat.service.ts:247`) отдаёт
`senderUserId: string | null`, `isSystemMessage: boolean`,
`voiceDurationSec?: number`, `messageWeight?: number`. Фронтовый `ChatMessage`
(`lib/chat-api.ts`) был объявлен без трёх последних полей и с
`senderUserId: string` — без `null`.

Расхождение реальное, не гипотетическое: `advanceStageIfReady`
(`chat.service.ts:1160`) создаёт системные сообщения (`senderUserId: null`,
`isSystemMessage: true`) на переходах этапа 1→2 и 2→3, они есть в сиде
(`prisma/seed/chat.ts:298`) и воспроизводятся на `demo@seed.yuni.local`.

Последствия в `messages/page.tsx`:

- `isMe = msg.senderUserId === user?.id` — для системного сообщения `false`,
  рисуется пузырём собеседника;
- группировка по равенству `senderUserId` — два `null` считаются одним
  отправителем, системные сообщения склеиваются друг с другом;
- в списке диалогов последнее системное сообщение показывалось репликой
  собеседника, без какого-либо признака, что это не реплика;
- голосовое сообщение (`voiceDurationSec`, в сиде — 30 сек от Игоря) не
  имело во фронтовом типе поля вообще и рендерилось как обычный текст.

Проверено полностью по коду `chat.service.ts` (не по формулировке
постановки) — расхождений с тем, что было заявлено, не нашлось.

## Решение

**Контракт** (`lib/chat-api.ts`): `senderUserId: string | null`,
добавлены `isSystemMessage: boolean`, `voiceDurationSec?: number`,
`messageWeight?: number`.

**Рендер** — три случая вместо двух, решение вынесено в чистую функцию
`features/chat/message-render.ts`:

- `getMessageBubbleKind(message, currentUserId): "mine" | "other" | "system"`
  — ветвится по `isSystemMessage`, не угадывает по `senderUserId === null`;
- `shouldGroupWithPrevious(current, previous)` — системное сообщение не
  группируется ни с предыдущим, ни со следующим (оба явно исключены, не
  через побочный эффект `null === null`).

Выделение в отдельный файл оправдано тем, что ветвление стало
трёхсторонним — тот же принцип, что `features/profile/form-state.ts` в
Task 076. Покрыто фронтовым Jest (`message-render.test.ts`, 11 тестов).

**`messages/page.tsx`**:

- системное сообщение — по центру, симметричный `border-radius` (без
  «хвостика» обычного пузыря), фон/текст — `var(--muted)` /
  `var(--muted-foreground)`, radius — `var(--shape-radius-md)`. Токены есть
  в `globals.css` — использованы как есть. Остальной файл написан
  литеральными `oklch(...)` в инлайн-стилях (отдельный долг, зафиксирован в
  `CLAUDE.md`) — не трогался за пределами нового системного бабла;
- список диалогов: если последнее сообщение системное — курсив,
  `var(--muted-foreground)`, без префикса «Ты:» (раньше система молча
  получала вид реплики собеседника без какого-либо префикса вовсе);
- голосовое сообщение — иконка `Mic` (lucide) + `m:ss` над текстом внутри
  обычного пузыря. Не плеер: полноценный voice UI — Task 068, здесь только
  чтобы сообщение не выглядело обычным текстом.

**Backend contract test** (`chat.service.spec.ts`, новый `describe`):
пинит точный набор ключей `ChatMessageView` через `Object.keys().sort()` на
трёх фикстурах — обычное/голосовое/системное сообщение, вызванных через
`getMessages` (единственный публичный путь, где `senderUserId: null`
попадает в ответ — `sendMessage` его не даёт никогда). `toEqual()` для этого
не подошёл бы: Jest не отличает отсутствующий ключ от ключа со значением
`undefined`, а именно на этом отличии держится условное добавление
`voiceDurationSec`/`messageWeight` в `toMessageView`.

Осознанное ограничение: тест защищает только от того, что бэкенд **сам не
заметит** смену своего контракта — красным падает у того, кто трогает
`toMessageView`, в том же PR. Прямой сверки с `apps/frontend/lib/chat-api.ts`
здесь нет — на это нужен общий пакет (Task 077, когда до него дойдёт), а
переиспользовать text-parse подпорку из Task 076 для этого случая посчитали
менее честным вариантом, чем backend-side pinning.

## Evidence

Все четыре пункта — negative control: сломать проверяемую логику, показать
красный прогон, вернуть, показать зелёный.

**Frontend** (`features/chat/message-render.test.ts`):

- `getMessageBubbleKind` без ветки `isSystemMessage` → падает
  `returns 'system' for a system message, regardless of senderUserId`;
- `shouldGroupWithPrevious` без исключения системных → падает
  `is false between two consecutive system messages` (единственный кейс,
  который реально изолирует необходимость гварда: два системных сообщения
  оба имеют `senderUserId: null`, и без явного исключения `null === null`
  склеивает их так же, как обычную пару).

**Backend** (`chat.service.spec.ts`, `ChatMessageView shape contract`):

- убран `if (voiceDurationSec !== null)` guard, поля добавляются всегда →
  падают тесты `regular`/`system` на лишних ключах (`voiceDurationSec`,
  `messageWeight`);
- `senderUserId: message.senderUserId ?? ''` → падает assertion
  `senderUserId === null` в системном кейсе — отдельное свойство от набора
  ключей, отдельный красный прогон.

**Прогоны** (локально, вне Docker):

## Визуальная проверка

Выполнена через `chrome-devtools-mcp` на `localhost:3000`, вход
`demo@seed.yuni.local`, диалог с Игорем (единственный демо-диалог на
этапе 2 — системное сообщение о переходе 1→2 и голосовое 30 сек от
Игоря). Оба вьюпорта, `list_console_messages` на каждом экране.

**Помеха перед проверкой.** В этом диалоге после системного сообщения и
голосового обнаружились три «ручных» тестовых сообщения (`1111`/`2222`/
`3333`, отправлены demo-пользователем 2026-08-19 — явно не часть сида).
Из-за них список диалогов показывал последним сообщением `Ты: 3333`, а не
системное — то есть сценарий «последнее сообщение в списке — системное»
не воспроизводился. С подтверждения владельца три строки удалены из
`messages` напрямую в Postgres (id `4453fc88…`, `962aa394…`, `5137a2a5…`).
Реальный «последний = системное» кейс в сиде тоже не встречается (после
системного в переписке идут ещё 8 реплик) — с подтверждения владельца
`created_at` системного сообщения (`ee1cd2f4-0522-4327-9ce9-912c68029868`)
временно сдвинут на конец диалога для скриншотов списка, затем возвращён
к исходному значению `2026-08-17 14:58:16.823+00`. После проверки состояние
БД сверено: 19 сообщений в диалоге, `created_at` системного восстановлен —
идентично сиду.
