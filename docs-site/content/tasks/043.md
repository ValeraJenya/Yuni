## Статус

`review` · P1

## Связь

Извлечено из Task 027.

## Finding

При одновременных первых ответах оба участника могут прочитать игру до ответа другого. В `READ COMMITTED` ни один запрос не выставит `ChatGame.completedAt`, хотя две `GameAnswer` уже существуют.

## Scope

Сделать запись ответа, определение completion и возможный stage transition конкурентно безопасными.

## Acceptance

- concurrent answers завершают игру ровно один раз;
- transition/system message создаются ровно один раз;
- сценарий доказан real-PostgreSQL race test.

## Что сделано

Метод `answerGame` в `apps/backend/src/modules/chat/chat.service.ts` переработан:

- Убран предварительный `findFirst` вне транзакции.
- Внутри `$transaction` добавлен `SELECT ... FOR UPDATE` через `tx.$queryRaw` — сериализует доступ к строке `chat_games`, второй параллельный запрос физически ждёт коммита первого.
- Проверка `completedAt` и `postponedUntil` выполняется по данным из `FOR UPDATE`-блокировки — гонка исключена.
- Определение completion перенесено на `existingAnswers.length + 1 >= 2` (findMany на уже закоммиченные ответы внутри транзакции).

Unit-тесты в `apps/backend/src/modules/chat/chat.service.spec.ts` обновлены:
мок `tx.$queryRaw` заменяет прежний `chatGame.findFirst`, мок `gameAnswer.findMany` заменяет `gameAnswer.count`.

## Доказательство фикса

`apps/backend/test/game-race.e2e-spec.ts` — интеграционный тест на реальном Postgres:

1. Регистрирует двух пользователей.
2. Создаёт conversation со stage 1 и один уже завершённый game (pre-condition для stage transition).
3. Запускает `answerGame` дважды параллельно (`Promise.all`) на одну игру.
4. Проверяет: `completedAt` выставлен, `gameAnswer` ровно 2 строки, `conversation.stage = 2`, system message ровно один раз.

Без фикса оба запроса видят count = 1 и ни один не завершает игру — тест упал бы на `expect(finalGame.completedAt).not.toBeNull()`.
