Статус: in_progress
Приоритет: P3

Описание: Verified-baseline расходится с git-историей — процессный пункт.

Заходов на задачу было четыре, считая текущий: PR #33 (`75d527c`),
PR #35 (`dbdac85`), PR #67 (`b30ce10`) и синхронизация на `42db25f`. Задача не
закрывается статусом «done», потому что каждый раз расхождение возвращалось.

Что известно про причины на момент четвёртого захода:

- **Момент обновления.** Документация правится отдельной задачей постфактум, а
  не тем PR, который меняет состояние. Между синхронизациями накапливается по
  два-три десятка PR.
- **Охват.** Каждая синхронизация трогала только часть документов. PR #67
  привёл в порядок `docs/ROADMAP.md`, `docs/PROJECT_STATE.md` и страницы задач,
  но не тронул `AI_CONTEXT.md`, `docs/FEATURES.md` и зеркала
  `docs-site/content/project/` — они так и остались на commit `5779763` от
  2026-07-21.
- **Механика хранения.** Статусы живут в markdown-таблицах, которые правит
  почти каждая feature-ветка. Merge `6d55e21` при разрешении конфликта в
  таблице «Выполнено» потерял две строки — 030 и 071 присутствуют в обоих
  родителях и отсутствуют в результате. Ошибка невидима в diff-е ветки и
  необнаружима без сверки с git log.
- **Дублирование.** Одни и те же факты записаны в пяти местах вручную, без
  скрипта синхронизации, при этом `docs-site/content/project/` публикуется
  наружу на GitHub Pages.
- **Состояние ветки/PR.** Утверждения о состоянии ветки или PR («PR не
  открыт», «ветка готова к пушу») истинны только на момент написания. Такое
  утверждение становится ложью в момент мержа, и обновлять его некому: тот,
  кто мержит, документ уже не редактирует. Средство — не напоминание, а
  запрет: состояние ветки и PR живёт в git и на GitHub, где оно актуально
  по определению; в `ROADMAP.md` попадает только то, что останется правдой
  после мержа — номер PR, хеш мержа, что сделано. Зафиксировано на
  собственном примере: абзац с формулировкой этого класса был написан в
  коммите, который чинил предыдущий экземпляр того же класса, и сам
  содержал новый — напоминание существовать в тот момент, когда оно нужно,
  не помогло.

## Acceptance

- verified-baseline в каждом документе соответствует `main`;
- расхождение не может накопиться незамеченным между синхронизациями.

Второй пункт статусной правкой не закрывается — нужен процессный механизм.
