## Finding

Видимость профиля в БД управляется двумя независимыми булевыми полями:

```prisma
model Profile {
  isDiscoverable Boolean @default(true) @map("is_discoverable")   // schema.prisma:146
  @@index([isDiscoverable, country, city])                        // schema.prisma:154
}

model PrivacySettings {
  discoverable Boolean @default(true)                             // schema.prisma:417
}
```

Discovery требует **оба**: `discovery.service.ts:146` фильтрует по
`isDiscoverable: true`, а `:155` — по `privacySettings.is.discoverable: true`.

`assertCanAccessProfile` знал только про первое:

```ts
// access-control.ts:87-91, до фикса
const visibilityMode = profile.privacySettings?.profileVisibilityMode ?? ProfileVisibilityMode.open;

if (!profile.isDiscoverable || visibilityMode !== ProfileVisibilityMode.open) {
  throw new ForbiddenException(FORBIDDEN_MESSAGE);
}
```

Поля `discoverable` не было даже в интерфейсе `ProfileAccessResource`
(`access-control.ts:21-26`).

После PR #74 у обоих флагов появился свой переключатель в UI, с почти
неразличимыми подписями: анкета → `isDiscoverable`
(`features/profile/components/profile-form-fields.tsx:169`, «Показывать в
поиске»), настройки → `discoverable` (`app/(app)/settings/privacy/page.tsx:116`,
«Показывать анкету в ленте»).

Отсюда сценарий дефекта: человек выключает тумблер в настройках приватности,
исчезает из выдачи Discovery — и при этом остаётся полностью открыт по прямой
ссылке `GET /profiles/:handle` и доступен для лайка. Настройка выглядит
работающей ровно настолько, чтобы ей поверить.

## Два пути, а не один

Через `assertCanAccessProfile` ходят два вызова, и чинить нужно оба:

| Вызов | Откуда приходит `privacySettings` | Состояние до фикса |
| --- | --- | --- |
| `profiles.service.ts:115` (`GET /profiles/:handle`) | `publicProfileInclude` тянет `privacySettings` целиком | данные были, не хватало только проверки |
| `likes.service.ts:216` (лайк / скип) | `targetProfileSelect` выбирал из `privacySettings` **только** `profileVisibilityMode` | данных не было вообще |

Это ключевая деталь задачи: правка одного `access-control.ts` закрыла бы
публичный просмотр и молча не сработала бы на лайках — `discoverable` приходил
бы `undefined` и проваливался в фолбэк.

## Решение

`discoverable` добавлен в `ProfileAccessResource.privacySettings` и в условие
`assertCanAccessProfile`: профиль недоступен постороннему, если выключен любой
из двух флагов. Ветка владельца (`profile.userId === currentUserId`) не
менялась — человек всегда видит себя.

`targetProfileSelect` в `likes.service.ts` расширен на `discoverable: true`,
чтобы флаг реально доезжал до проверки.

Отсутствующие `privacySettings` трактуются как `discoverable === true` — по
`@default(true)` в схеме. Строка `PrivacySettings` создаётся вместе с
пользователем при регистрации (`auth.service.ts:100`), поэтому `null` в норме не
встречается: строгий дефолт ничего бы не защитил, а в редком случае битых данных
отрезал бы человека от собственной видимости без причины.

Здесь остаётся сознательное расхождение с Discovery: там `privacySettings.is`
при `null` просто не матчится, то есть профиль без настроек из ленты выпадает, а
access-control его пропускает. Разойтись в эту сторону безопаснее, чем менять
поведение для существующих данных в рамках security-фикса; зафиксировано как
известное, отдельно не чинилось.

Схема и миграции не трогались. Оба UI-переключателя оставлены как есть,
frontend не менялся.

## Evidence

Покрыты оба пути.

`common/security/access-control.spec.ts` — дополнен существующий
`describe('assertCanAccessProfile')`:

- владелец при выключенном `discoverable` — доступ есть;
- посторонний при выключенном **только** `discoverable` — `Forbidden`;
- отдельный кейс сравнивает выключение каждого флага по одному и проверяет, что
  поведение одинаковое;
- `privacySettings: null` — доступ есть (зафиксирован фолбэк выше).

`modules/likes/likes.service.spec.ts` — юнит-тесты на сервис, отдельный e2e не
заводился:

- `likeProfile` и `skipProfile` при выключенном `discoverable` дают `Forbidden`,
  `like.create` не вызывается;
- отдельный тест проверяет сам `select`: `profile.findUnique` должен запрашивать
  `privacySettings.select.discoverable`. Он нужен потому, что Prisma в юнит-тесте
  замокана и фикстуру возвращает независимо от `select` — без такой проверки
  откат правки в `likes.service.ts` не поймался бы ни одним поведенческим тестом.

Регрессия воспроизведена в обе стороны, отдельно по каждому файлу:

- откат условия в `access-control.ts` → падают 3 теста в обеих сюитах
  (`rejects other users when only the privacy discoverable flag is off`,
  `treats both discoverability flags the same way when each is turned off alone`,
  `LikesService › rejects LIKE and SKIP when the privacy discoverable flag is off`);
- откат `discoverable` из `targetProfileSelect` → падает 1 тест
  (`selects the privacy discoverable flag so the access check can see it`).

Два отката ловятся разными тестами и не перекрывают друг друга — это и
подтверждает, что закрыты оба пути, а не один.

Прогоны:

- `npm run lint` (apps/backend) — чисто;
- `npm run typecheck` (apps/backend) — чисто;
- `npm test` (apps/backend) — 20 сюит, 217 тестов, зелёные.

`test:e2e` не запускался: задача не добавляла e2e-спеков, покрытие юнит-уровня
согласовано в scope-check.

Визуальная проверка по `CLAUDE.md` не проводилась и не требуется: изменений
вёрстки в задаче нет.

## Осталось за рамками

Главный открытый вопрос — схлопывание двух полей в одно. Сейчас закрыта дыра, но
не устранена её причина: два источника истины и два почти одинаковых тумблера в
UI остаются на месте, и следующий код, который забудет про один из них,
воспроизведёт тот же класс дефекта. Решение принимает владелец отдельно;
аргументы за `PrivacySettings.discoverable` как единственный источник — в
описании задачи.

Расхождение дефолтов при `privacySettings === null` между Discovery и
access-control описано выше и намеренно оставлено.
