## Фактически реализовано

### Схема

- `Conversation`: `stage`, timestamps этапов, voice totals участников.
- `Message`: nullable `voiceDurationSec`, `messageWeight`, `isSystemMessage`; системный sender может быть `null`.
- Модели `ChatGame`, `GameAnswer` и `ConversationStarter`.
- Новый conversation создаётся на stage 1; stage меняется только backend-ом.

### Staged endpoints

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/chat/conversations/:conversationId/stage` | stage, timestamps, voice limits |
| `GET` | `/chat/starters` | до четырёх активных стартовых фраз |
| `GET` | `/chat/conversations/:conversationId/game/current` | текущая игра или `null` |
| `POST` | `/chat/conversations/:conversationId/game/postpone` | один postpone на минуту |
| `POST` | `/chat/conversations/:conversationId/game/:gameId/answer` | ответ участника |

### Правила

- Stage 1: voice запрещён; game thresholds — 5 и 10 message weight.
- Stage 2: client-provided voice duration ограничивается 60 секундами на сообщение и persisted total 90 секунд на участника; game thresholds — 5, 10 и 15.
- Stage 3 снимает staged-запреты на voice/attachment message type, но upload/storage файлов не реализован.
- Text/attachment weight — 1; voice — `MAX(1, FLOOR(duration / 15))`.
- Две завершённые игры переводят stage 1→2, три — stage 2→3.
- Переход создаёт системное сообщение (`isSystemMessage=true`, `senderUserId=null`).
- Один пользователь не может ответить на игру дважды; postpone разрешён один раз.

## Реализовано частично

- Последовательный voice send clamp-ит клиентское значение и увеличивает persisted total в транзакции сообщения.
- Unit tests покрывают основную staged-логику, но не PostgreSQL races.
- Игровые вопросы встроены в код; starters зависят от содержимого отдельной таблицы.
- Attachment message type имеет stage gate, но transport/storage вложений отсутствует.

## Подтверждённые gaps

1. Concurrent first answers могут не выставить `ChatGame.completedAt` при `READ COMMITTED` — Task 043.
2. Concurrent voice sends обходят total 90 секунд; duration доверяет клиенту, реальной проверки/обрезки audio нет — Task 044.
3. `conversation_starters` не имеет seed, поэтому чистая БД возвращает пустой список — Task 045.
4. Frontend считает `ChatMessage.senderUserId` обязательным `string`, хотя system message возвращает `null`; contract tests отсутствуют — Task 048.

## Продуктовый дизайн

Это целевое поведение, а не полностью доказанный текущий факт:

| Этап | Возможности | Переход |
|---|---|---|
| 1 | text, starters, 2 игры | 2 завершённые игры |
| 2 | text + voice с лимитами, 3 игры | 3 завершённые игры |
| 3 | text + voice + attachments | конечный |

Целевой production voice flow должен определять длительность по реальному файлу и физически обрезать его до остатка лимита. Текущий backend этого не делает.
