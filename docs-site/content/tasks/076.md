## Статус

`review` · P2

## Finding

В `apps/frontend` не было ни одного теста и ни одного тест-раннера — в
`package.json` только `dev`/`build`/`start`/`lint`/`typecheck`. За последний
месяц во фронт уехала настоящая логика (профиль, онбординг, язык, заглушки
аватара), и её проверяли только глаза через `chrome-devtools-mcp`.

Backend уже тестируется Jest 29; frontend оставался без регрессионной сетки
для чистой логики.

## Acceptance

- Jest тот же, что на бэкенде (29.7.0 / ts-jest 29.2.5 / @types/jest 29.5.14),
  не второй фреймворк в монорепо;
- алиас `@/...` и TypeScript работают в тестах;
- `pnpm --filter frontend test` запускается из корня и проходит;
- покрыты `features/profile/form-state.ts`, `lib/default-avatar.ts`,
  `lib/utils.ts`, один-два `lib/*-api.ts`;
- отдельно закреплено расхождение обязательных полей frontend/backend
  (см. «Решение»);
- никаких тестов на рендер компонентов и `@testing-library` — это отдельное
  решение с более высокой стоимостью поддержки;
- каждый тест подтверждён красным прогоном на намеренно сломанной логике.

## Источник

Задача владельца: завести тестовый раннер и закрыть тестами код, который
сейчас не проверяется ничем.

## Решение

### Раннер

`jest.config.js` (не `.cjs` — см. ниже) с `preset: 'ts-jest'`,
`moduleNameMapper` для `@/*` и отдельным `tsconfig.jest.json`, который
переопределяет `module`/`moduleResolution` на `commonjs`/`node` — основной
`tsconfig.json` фронта использует `moduleResolution: "bundler"`, с которым
Jest (CommonJS `require`) не работает напрямую.

`jest.config.cjs` пришлось переименовать в `jest.config.js`: `eslint-config-next`
регистрирует плагин `react-hooks` только для файлов
`**/*.{js,jsx,mjs,ts,tsx,mts,cts}` — `.cjs` в этот список не входит. Правило
`react-hooks/purity` в `eslint.config.mjs` при этом задано без ограничения на
`files` и применяется ко всем файлам, включая `.cjs`, для которых плагин не
зарегистрирован — `eslint .` падал с «could not find plugin react-hooks» на
самом файле конфигурации Jest. В `package.json` фронта нет `"type": "module"`,
поэтому `.js` с `module.exports` остаётся CommonJS — переименование ничего не
меняет в поведении раннера.

### Покрытие

Четыре точки чистой логики, без рендера компонентов:

- `features/profile/form-state.ts` — dirty-сравнение (включая нормализацию
  `null`/`""` и пробелов), сборка `UpdateProfileRequest`, `missingRequiredFields`.
  Отдельно закреплено: пустая строка уезжает как `null`, а не как `""` — иначе
  бэкенд посчитает поле заполненным и анкету полной;
- `lib/default-avatar.ts` — `defaultAvatarUrl`/`avatarUrlOrDefault`:
  female/male, нормализация регистра и пробелов, нейтральный вариант для
  пустого и нераспознанного значения;
- `lib/utils.ts` — `cn()`, включая разрешение конфликтов Tailwind-утилит;
- `lib/auth-api.ts` — сериализация тела запроса (JSON vs `FormData`,
  `Content-Type`), `Authorization` header, разбор ошибок бэкенда (`message`
  как массив/строка, fallback на `statusText`/generic message).

### Расхождение обязательных полей frontend/backend

Task 070 чинил ровно это: список обязательных полей во фронте
(`PROFILE_FORM_FIELDS` в `form-state.ts`) и `PROFILE_COMPLETION_FIELDS` на
бэкенде (`profile-completion.policy.ts`) должны совпадать — иначе человек
заполнит форму, нажмёт «Готово» и всё равно не попадёт в выдачу. Источник один
архитектурно, но ничем не закреплён, а бэкенд свою половину меняет отдельными
PR.

`apps/frontend` не зависит от `apps/backend` (независимые пакеты монорепо),
прямой импорт невозможен. Рассмотренные варианты:

1. **Frontend-тест читает backend-файл как текст** (`fs.readFileSync` +
   regexp) — без новой зависимости, ловит расхождение уже сегодня; хрупко к
   рефакторингу бэкенд-файла (переименование константы, смена формата
   массива).
2. **Общий пакет монорепо** с `PROFILE_COMPLETION_FIELDS`, из которого
   импортируют обе стороны — архитектурно верно, компилятор гарантирует
   единый источник вместо regexp'а, но требует новой workspace-структуры и
   правок backend module resolution — отдельная задача, шире scope «тестового
   раннера фронта».
3. **Backend-тест читает frontend-файл** — тот же тип хрупкости, что вариант
   1, но со стороны бэкенда; прямо запрещён этой задачей («не трогай
   бэкендные тесты и их конфиг»).

Выбран вариант 1 — `features/profile/required-fields.contract.test.ts`,
реализован в рамках этой задачи. С одним обязательным усилением: наивный
regexp-парсинг может тихо дать пустой список, если бэкенд переименует
константу или сменит формат массива, — сравнение пустого списка с фронтовым
могло бы либо упасть по случайной причине, либо (при другой форме сравнения)
пройти зелёным именно тогда, когда перестало что-либо проверять. Тест сначала
проверяет, что парсинг вообще нашёл ожидаемое число полей (захардкожено — 8:
`displayName`, `birthDate`, `bio`, `gender`, `lookingFor`, `city`, `country`,
`photo`) и падает с отдельным сообщением, если это не так, отдельно от
сообщения о реальном расхождении списков.

Вариант 2 заведён в `ROADMAP.md` как Task 077 (`idea`, `P3`) — вариант 1
стопгап, не окончательное решение.

## Evidence

Для каждого теста — намеренная поломка проверяемой логики → красный прогон →
восстановление → зелёный прогон:

- `lib/utils.ts`: `cn` без `twMerge` → «resolves conflicting Tailwind utility
  classes» падает (`"px-2 px-4"` вместо `"px-4"`);
- `lib/default-avatar.ts`: убрана `.trim().toLowerCase()` → «normalizes
  casing» и «normalizes surrounding whitespace» падают (неверно уезжают в
  нейтральный аватар);
- `features/profile/form-state.ts`: `emptyToNull` перестаёт возвращать `null`
  для пустой строки → три теста `toUpdateProfileRequest` падают, ожидаемо
  получая `""` вместо `null`;
- `lib/auth-api.ts`: `parseError` перестаёт учитывать `body.message` → тесты
  на массив/строку сообщения об ошибке падают, получая `statusText` вместо
  сообщения бэкенда;
- `required-fields.contract.test.ts`: два независимых красных прогона —
  (а) `PROFILE_FORM_FIELDS` временно помечает `bio` не обязательным →
  падает тест сравнения списков (симуляция дрейфа, который чинил Task 070),
  «parser sanity» тест при этом остаётся зелёным; (б) regexp временно ищет
  несуществующее имя константы → падает «parser sanity» тест с отдельным
  сообщением о том, что парсер устарел, «mismatch»-тест при этом тоже падает
  (пустой список бэкенд-полей), но по другой, явно другой причине.

`pnpm --filter frontend test` — 6 test suites, 45 тестов, все зелёные —
перепрогнано после мержа `origin/main` (см. «Осталось за рамками» про
исходную неверную базу ветки).

`pnpm --filter frontend lint` — 18 предупреждений, столько же, сколько на
`main`: `react-hooks/set-state-in-effect` в
`components/landing/motion/in-view.tsx:43` (Task 075) на месте и учтён.
Первая версия тестового файла `form-state.test.ts` добавляла 19-е
предупреждение (неиспользуемая деструктуризация `isDiscoverable`) —
исправлено до коммита переписыванием через spread вместо
rest-деструктуризации.

`pnpm --filter frontend typecheck` (`next typegen && tsc --noEmit`) и
`next build` проходят без ошибок; тестовые файлы не попадают в собранные
роуты.

## Осталось за рамками

- Тесты на рендер компонентов и `@testing-library` — сознательно не делались,
  визуальную часть закрывает `chrome-devtools-mcp` по регламенту из
  `CLAUDE.md`.
- Вынос `PROFILE_COMPLETION_FIELDS` в общий пакет монорепо — Task 077,
  `idea`/`P3`. Пока не сделан, регрессия ловится regexp-парсингом (см.
  «Решение»), который переживёт дрейф значений, но не переживёт рефакторинг
  формата бэкенд-файла без обновления парсера в тесте.
- В постановке задачи ожидалось 7 полей в `PROFILE_COMPLETION_FIELDS`; по
  факту в `profile-completion.policy.ts` их 8 (`displayName`, `birthDate`,
  `bio`, `gender`, `lookingFor`, `city`, `country`, `photo`). Тест и evidence
  зафиксированы по фактическому состоянию кода, а не по ожиданию из
  постановки.
- Ветка изначально создавалась от `8feff3b` (PR #77), а не от `d199fe8`, как
  было заявлено в первом отчёте по задаче, — отстала на шесть мержей
  (#78–#83). Из-за этого первый прогон lint дал 17 предупреждений вместо
  верных 18: `components/landing/motion/in-view.tsx` с найденным Task 075
  предупреждением `react-hooks/set-state-in-effect` появился только в PR #78
  и на устаревшей базе ветки не существовал. Обновлено через
  `git merge origin/main`; конфликт в `docs/ROADMAP.md` (дублирующиеся
  строки Task 070/072, уже перенесённые в «Выполнено» на `origin/main`, и
  строки Task 073–075, которых не было на старой базе) разрешён отдельно —
  первая попытка слияния закоммитила файл с неразрешёнными
  `<<<<<<<`/`=======`/`>>>>>>>` маркерами, это исправлено следующим коммитом.
  Контрактный тест и счётчик полей (8) перепроверены против
  `profile-completion.policy.ts` в его текущем виде после PR #80/#82 —
  файл не менялся, оба прогона (зелёный и оба красных) подтверждены заново.
