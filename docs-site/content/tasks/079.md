## Статус

`review` · P2 — ветка `fix/task-079-public-console`.

## Finding

`AuthProvider` смонтирован в корневом layout (`apps/frontend/app/layout.tsx`).
Его mount-эффект (`apps/frontend/lib/auth-context.tsx:87-101`, до этой задачи)
безусловно вызывал `refreshSession()` → `POST /auth/refresh`. Для анонимного
посетителя это гарантированный 401 на `/`, `/join`, `/signin`,
`/forgot-password`, `/terms`, `/privacy`, `/help`.

Подавить вывод нельзя: строку `Failed to load resource: 401` печатает
сетевой слой браузера раньше, чем промис дойдёт до `.catch()`. `.catch()`
уже стоял в коде, ошибка была проглочена — строка в консоли оставалась
всё равно. Единственный путь — не делать запрос там, где он не нужен.

`useAuth`/`AuthProvider` реально используются только в: `(app)/layout.tsx`
(через `app-content.tsx`), `(auth)/layout.tsx`, `onboarding/layout.tsx`,
плюс страницы внутри `(app)/*`, `sign-in-form`, `sign-up-form`,
`use-settings-resource`. Лендинг (`app/page.tsx`), `/terms`, `/privacy`,
`/help` сессию не читают вообще.

`/join`, `/signin` и `/forgot-password` — особый случай: `(auth)/layout.tsx`
использует `isAuthenticated` и `isLoading`, чтобы увести уже залогиненного
человека с этих страниц (Task 070). Выключить bootstrap там означало бы
сломать этот редирект.

### Найденная ловушка

`(auth)/layout.tsx:57` — `if (isLoading || isAuthenticated)` рендерит
**только** экран «Загрузка», не рендерит `children` вообще. Если бы решение
свелось к «повесить bootstrap явным хуком в нужных layout-ах и не забыть
его туда поставить», забытый хук на новой публичной странице, которая позже
начала бы вызывать `useAuth()`, дал бы не деградацию и не ошибку в консоли,
а вечный белый экран — `isLoading` остался бы `true` навсегда, без единой
подсказки в консоли, откуда искать причину.

## Acceptance

- `/`, `/terms`, `/privacy`, `/help` не делают `POST /auth/refresh` и не
  печатают 401 в консоли;
- `/join`, `/signin`, `/forgot-password` — редирект уже залогиненного
  человека на эти страницы продолжает работать;
- анонимный заход на защищённый `(app)`-роут по-прежнему уводит на вход;
- перезагрузка страницы внутри `(app)` для залогиненного не разлогинивает;
- механизм структурно не может быть забыт — не держится на том, что кто-то
  не забыл смонтировать отдельный хук в нужном layout-е;
- закреплено тестом, включая негативный контроль (красный прогон на
  намеренно отключённом механизме).

## Решение

Рассматривались три варианта (изложены в постановке задачи):

1. Явный хук `useAuthBootstrap()`, монтируемый только в
   `(app)/layout.tsx`, `(auth)/layout.tsx`, `onboarding/layout.tsx`;
2. Маркер прошлой сессии на клиенте;
3. Ленивый вызов по первому обращению к сессии.

Первая итерация решения — вариант 1 (отдельный хук в трёх layout-ах,
`AuthProvider` только для контекста). Проблема, найденная при разборе
`(auth)/layout.tsx:57`: если кто-то через полгода добавит `useAuth()` на
новую публичную страницу и забудет туда же поставить `useAuthBootstrap()`,
получится не заметный дефект, а немой вечный спиннер — ни ошибки, ни
стектрейса, ни подсказки, что смотреть нужно именно в этот хук.

Решение переформулировано так, чтобы забыть механизм было структурно
невозможно: **сам `useAuth()` инициирует bootstrap** в собственном
`useEffect`, а не полагается на то, что кто-то отдельно смонтирует
специальный хук в правильном layout-е.

```
useAuth()
  → useContext(AuthContext)
  → useEffect(() => { ensureBootstrapped() }, [ensureBootstrapped])
  → возвращает контекст без ensureBootstrapped
```

`AuthProvider` предоставляет `ensureBootstrapped()` — идемпотентную
функцию на `useRef`-флаге: первый вызов запускает `refreshSession()` и
снимает `isLoading` в `finally`, все последующие вызовы (в том числе от
нескольких `useAuth()`-потребителей на одной странице, смонтированных в
один тик) — no-op. `ensureBootstrapped` не входит в публичный тип, который
возвращает `useAuth()` — деструктурируется наружу из результата, доступен
только внутри самого хука.

Любая страница, где `useAuth()` не вызывается ни разу (все четыре
публичные), не запускает `refreshSession()` вообще — контекста никто не
читает, `AuthProvider` просто хранит начальное состояние.

### `isLoading`

Начальное значение (`useState(true)`) не меняется. Причина, почему нельзя
стартовать с `false`: `(auth)/layout.tsx` на первом кадре при `isLoading:
false` и `isAuthenticated: false` успел бы отрисовать форму входа
залогиненному человеку до того, как асинхронный `refreshSession()` вообще
начался бы — мигание формы хуже, чем один лишний кадр загрузки.

`isLoading` снимается в `false` только когда `ensureBootstrapped()`
фактически отработал. Для четырёх публичных страниц, где `useAuth()` не
вызывается, `isLoading` просто никем не читается — потребителя нет. Если в
будущем кто-то добавит туда `useAuth()`, это автоматически запустит
`ensureBootstrapped()` через эффект самого хука — застрять в вечном
`isLoading: true` теперь невозможно структурно, а не потому, что кто-то не
забыл про отдельный хук.

## Evidence

Стек поднят локально (`pnpm --filter frontend dev` на порт 3000,
backend + Postgres — Docker Compose), анонимный контекст, через
`Claude_Browser`:

**Публичные страницы, `POST /auth/refresh` в сетевом логе / 401 в консоли:**

| Страница | До правки | После правки |
|---|---|---|
| `/` | 401 | нет запроса |
| `/terms` | 401 | нет запроса |
| `/privacy` | 401 | нет запроса |
| `/help` | 401 | нет запроса |
| `/join` | 401 | 401 (ожидаемо — нужен для редиректа залогиненных) |
| `/signin` | 401 | 401 (ожидаемо) |
| `/forgot-password` | 401 | 401 (ожидаемо) |

Проверено по факту: у `/`, `/terms`, `/privacy`, `/help` в сетевом логе
после захода на каждую из них не появилось ни одного нового
`POST /auth/refresh` — только унаследованный запрос от предыдущей
`/join`-навигации внутри той же сессии браузера. У `/join`, `/signin`,
`/forgot-password` — ровно по одному новому.

**Вход и сохранение сессии:** вход `demo@seed.yuni.local` (синтетический
seed-аккаунт из `apps/backend/prisma/seed/personas.ts`) → редирект на
`/discover`, карточки загрузились. Полная перезагрузка страницы на
`/discover` (`force: true` в `navigate`, эквивалент F5) →
`POST /auth/refresh → 200 OK`, сессия и данные остались — разлогинивания
нет.

**Редирект залогиненного (главный риск задачи):** залогиненным заход на
`/signin` → мгновенный редирект на `/discover`, форма входа не
отрисовалась. Тот же результат на `/join`.

**Анонимный заход на защищённый роут:** после `logout` (`POST /auth/logout
→ 200 OK`) заход на `/discover` → `POST /auth/refresh → 401` → редирект на
форму входа.

**Тест, `lib/auth-context.test.ts`** (новый, jsdom через
`@testing-library/react`, per-file `@jest-environment jsdom`, чтобы не
трогать общий `testEnvironment: 'node'` в `jest.config.js`):

- `AuthProvider` без потребителей → `refresh` не вызван;
- `useAuth()`-потребитель → `refresh` вызван ровно один раз, `isLoading`
  доходит до `false`;
- несколько `useAuth()`-потребителей на одной странице → всё равно один
  вызов `refresh` (ref-guard).

Негативный контроль: механизм временно отключён (закомментирован
`useEffect` в `useAuth()`) → 3 из 4 тестов красные — «calls refresh exactly
once», «resolves isLoading to false», «only one refresh with several
consumers». Тест «does not call refresh when no consumer» остаётся зелёным
и в отключённом состоянии — это ожидаемо, он не про этот механизм.
Механизм восстановлен → все 4 теста зелёные.

`pnpm --filter frontend test` — 8 test suites, 60 тестов, все зелёные.

`pnpm --filter frontend lint` — 17 предупреждений, baseline не вырос.

`pnpm --filter frontend exec tsc --noEmit` — без ошибок.

`pnpm --filter frontend exec next build` — проходит, все 16 статических
роутов на месте, включая семь публичных.
