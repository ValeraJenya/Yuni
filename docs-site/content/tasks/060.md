## Finding

`ParseUUIDPipe` применялся не во всех контроллерах. Полный обход показал, что
незакрытых точек ровно две — обе в `media.controller.ts`:

```ts
@Patch(':photoId/primary')
setProfilePhotoPrimary(
  @CurrentUser() currentUser: AuthenticatedUser,
  @Param('photoId') photoId: string,   // media.controller.ts:49
)

@Delete(':photoId')
deleteProfilePhoto(
  @CurrentUser() currentUser: AuthenticatedUser,
  @Param('photoId') photoId: string,   // media.controller.ts:58
)
```

`ProfilePhoto.id` объявлен `@db.Uuid`, а `media.service.ts:139` и `:180` делают
`findUnique({ where: { id: photoId } })`. На невалидном UUID Prisma бросает
`P2023`; `AllExceptionsFilter` не распознаёт `PrismaClientKnownRequestError` как
`HttpException`, уходит в ветку `logger.error` и отдаёт
`500 "Internal server error"` вместо `400`.

То есть пользовательский мусор в URL выглядел как отказ сервера и писался в
error-лог.

## Решение

`ParseUUIDPipe` добавлен в оба `@Param('photoId')`. Пайп ставится без аргумента
версии — ровно так же, как в `chat.controller.ts`. Формально
`gen_random_uuid()` генерирует v4 и можно было бы написать
`new ParseUUIDPipe({ version: '4' })`, но консистентность со всеми остальными
контроллерами важнее строгости: разнобой в правилах валидации сам по себе
источник ошибок.

`@Param('handle')` в `profiles.controller.ts:30` намеренно оставлен как есть.
`handle` — не UUID, и `ParseUUIDPipe` на нём сломал бы публичный просмотр
профиля. Он уходит в `findUnique` по колонке `String @unique`, поэтому Prisma
не падает и 500 не возникает; валидация формата там — вопрос гигиены, а не
дефекта, и тянет на отдельную мелкую задачу с `@Matches` на DTO.

`AllExceptionsFilter` не изменялся. Разбор Prisma-ошибок в фильтре — отдельная и
более крупная задача, см. «Осталось за рамками».

Сигнатуры `MediaService` не менялись.

## Осталось за рамками

Точечные пайпы закрывают path-параметры, но не закрывают **класс** ошибки. Та же
`P2023` продолжает утекать пятисоткой через query: `cursor` объявлен
`@IsOptional() @IsString()` без `@IsUUID()` сразу в двух независимых DTO —
общем `common/pagination/cursor-pagination.dto.ts` и собственном
`modules/discovery/dto/discovery-cards-query.dto.ts` — и уходит в Prisma по
uuid-колонке в пяти местах: `moderation.service.ts:180`, `chat.service.ts:349`,
`chat.service.ts:398`, `notifications.service.ts:183` (все как `cursor: { id }`)
и `discovery.service.ts:104` (как `cursor: { userId }`).

Заведено как Task 073. Руками не воспроизводилось — вывод сделан по чтению кода.

Отдельно остаётся вопрос, не должен ли `AllExceptionsFilter` сам мапить
`P2023`/`P2025` в 4xx: тогда класс ошибки закрывался бы централизованно, а не
пайпом на каждой точке входа.

Валидация `@Param('handle')` через `@Matches` на DTO — отдельная мелкая задача,
в ROADMAP пока не заведена.
